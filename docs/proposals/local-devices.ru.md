# Локальное обнаружение устройств и разделение репозитория на три библиотеки

**Статус:** шаг 1 выполнен — `YandexMusic.Ynison` выделен в отдельный пакет в 0.5.0, ядро стало
самодостаточным. Локальный протокол по-прежнему не исследован: всё, что ниже заголовка «Открытые
вопросы», считать неподтверждённым, а `YandexMusic.LocalDevices` пока не существует — пустой пакет
хуже, чем его отсутствие.

## Проблема

Пульт Ynison показывает только те устройства, которые вошли в Ynison-сессию аккаунта. В снятом с
живой сессии кадре (журнал запросов, клавиша `g` в меню) их ровно четыре:

| device_id | название | тип | офлайн | can_be_player |
|---|---|---|---|---|
| `71627e95…` | OnePlus CPH2747 | ANDROID | нет | да |
| `<это приложение>` | YandexMusic .NET | WEB | нет | нет |
| `5315b78…` | YandexMusic .NET | WEB | да | нет |
| `dbf5653…` | YandexMusic .NET | WEB | да | нет |

Колонок нет вообще — ни в простое, ни в каком-либо виде, и в кадре нет поля, которое могло бы их
скрывать. Сервер просто не помещает их в сессию.

При этом официальное приложение предлагает колонки в той же сети Wi-Fi **даже когда на колонке чужой
аккаунт**. Протокол уровня аккаунта так не умеет по построению. Значит, список устройств в
официальном клиенте — объединение двух источников:

1. **Ynison** — устройства *этого аккаунта*, находящиеся в сессии. Уже реализовано.
2. **Локальное обнаружение** — всё, что откликнулось *в этой сети*, независимо от аккаунта. Нет.

Этот issue — про второй источник и про перестройку репозитория, которой он требует.

## Почему это требует перестройки

Сейчас `YandexMusic` — один пакет, содержащий и REST API, и Ynison, связанные через
`IYandexMusicClient.CreateYnisonClient()`. Добавить в тот же пакет третью подсистему — значит
заставить каждого потребителя REST API таскать за собой websocket-клиент, mDNS-ответчик и локальный
TLS-стек, которые он никогда не вызовет.

Подавляющему большинству нужен REST API и ничего больше. Это должно остаться правдой.

### Целевая раскладка

```
YandexMusic                 REST Music API. Зависит только от BCL.
YandexMusic.Ynison          Состояние и пульт уровня аккаунта. Зависит от YandexMusic.
YandexMusic.LocalDevices    Обнаружение и управление в своей сети. Зависит от YandexMusic.
YandexMusic.DependencyInjection   Без изменений: AddYandexMusic() для ядра.
```

Правила:

- `YandexMusic` никогда не ссылается на два других. Он самодостаточен и полезен сам по себе — это то
  ограничение, под которое подстраивается всё остальное.
- `YandexMusic.Ynison` и `YandexMusic.LocalDevices` не ссылаются друг на друга. Кому нужен объединённый
  список устройств, как в официальном приложении, берёт оба и объединяет сам; помощник, который делает
  объединение, может появиться позже отдельным пакетом, когда обе половины будут готовы.
- Все три выпускаются из этого репозитория на одной версионной линии, чтобы «репозиторий YandexMusic
  закрывает все потребности по работе с сервисом» выполнялось без разнесения работы по репозиториям.

### Единственное ломающее изменение, которое для этого нужно — сделано в 0.5.0

`IYandexMusicClient.CreateYnisonClient()` — та самая связка, которая мешала разделению: интерфейс ядра
называл тип из Ynison. Метод уехал из ядра и стал методом расширения, которое поставляет пакет Ynison:

```csharp
// до 0.5.0, на интерфейсе ядра
IYnisonClient CreateYnisonClient(string? deviceId = null, YnisonClientOptions? options = null);

// с 0.5.0, в YandexMusic.Ynison
public static class YandexMusicClientYnisonExtensions
{
    public static IYnisonClient CreateYnisonClient(
        this IYandexMusicClient client,
        string? deviceId = null,
        YnisonClientOptions? options = null);
}
```

Места вызова не изменились — `client.CreateYnisonClient()` по-прежнему компилируется, — но теперь
нужен `using YandexMusic.Ynison;`, а из интерфейса ядра метод исчез. Токен берётся из
`client.Authentication.Session.AccessToken`, он и так был публичным.

Заодно уехали две мелочи, невидимые для вызывающего кода: `YandexMusicYnisonException` теперь
поставляется из сборки Ynison (namespace не менялся, так что блоки `catch` компилируются как прежде),
и вместе с ним переехали protobuf-JSON-конвертеры — других потребителей у них не было. Ядро больше
вообще не ссылается на `System.Net.WebSockets`.

`YandexMusic.LocalDevices` получает такое же оформление, чтобы все три точки входа читались одинаково.

## Объём YandexMusic.LocalDevices

Три отделимых части, в порядке зависимости:

1. **Обнаружение.** Найти колонки в текущей сети и сообщить id, имя, модель, адрес и доступность.
   Чисто локально, аккаунт не участвует.
2. **Авторизация.** Получить то, что требует локальный канал управления. Именно эта часть трогает
   бэкенд Яндекса и именно она понята хуже всего.
3. **Управление.** Подключиться к устройству и рулить им: play/pause, следующий/предыдущий, громкость,
   статус.

Разумная первая веха — **только обнаружение**: `LocalDeviceScanner`, возвращающий то, что есть в сети.
Оно ценно само по себе (пульт сможет показать колонки серым и объяснить, почему ими пока нельзя
управлять), проверяется без каких-либо учётных данных и снимает риск с остального.

### Набросок поверхности

```csharp
public interface ILocalDeviceScanner
{
    IAsyncEnumerable<LocalDevice> DiscoverAsync(TimeSpan window, CancellationToken cancellationToken = default);
}

public sealed record LocalDevice(string DeviceId, string Name, string Model, IPEndPoint Endpoint);
```

`IAsyncEnumerable`, а не список: обнаружение — это поток ответов, приходящих в течение окна, и UI
хочет показывать каждое устройство в момент его отклика.

## Открытые вопросы — ни на один ответа пока нет

Всё это требует исследования с перехватом трафика официального приложения до написания кода. Я ничего
из перечисленного не проверял, и issue не должен делать вид, что это не так.

- **Механизм обнаружения.** Сильная гипотеза — mDNS/DNS-SD (тип сервиса обычно называют
  `_yandexio._tcp`), но это надо подтвердить на проводе и заодно понять, что лежит в TXT-записях.
- **Цена зависимости.** В BCL нет mDNS. Либо брать зависимость (Makaretu.Dns, Zeroconf), либо
  реализовывать нужное подмножество. Для библиотеки, которая заявляет ядро без зависимостей, этот
  выбор заслуживает отдельного обсуждения — он попадает только в `LocalDevices`, но это всё равно
  зависимость.
- **Транспорт и TLS.** Локальное управление, по имеющимся сведениям, — websocket к самому устройству,
  с сертификатом, который не построит цепочку до публичного корня. Как именно его проверять, должно
  быть осознанным и задокументированным решением, а не «принимаем всё подряд».
- **Учётные данные.** Что устройство требует, чтобы принять команду, откуда это берётся и сколько
  живёт. Если это надо получать с бэкенда Яндекса, то эндпоинт недокументирован и лежит вне Music API —
  что как раз аргумент держать его в этом пакете, а не в ядре.
- **Управление под чужим аккаунтом.** Официальное приложение управляет колонками с чужими аккаунтами.
  Верно ли это для любого устройства в сети или только в каком-то состоянии сопряжения — это
  существенно меняет модель безопасности функции и должно быть понято до выпуска.
- **Охват платформ.** Поведение mDNS различается между Windows/Linux/macOS и ломается во многих
  корпоративных и гостевых сетях. Библиотека должна аккуратно вырождаться в «ничего не найдено», а не
  зависать.

## Вне объёма

- Обёртка над платформой умного дома вообще (лампы, розетки, сценарии). Речь только о точках
  воспроизведения музыки.
- Объединение двух списков устройств внутри любого из пакетов. Это уровнем выше обоих.
- Голосовое взаимодействие с ассистентом.
