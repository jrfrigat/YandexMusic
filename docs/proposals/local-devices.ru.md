# Локальное обнаружение устройств и разделение репозитория на три библиотеки

**Статус:** шаг 1 выполнен — `YandexMusic.Ynison` выделен в отдельный пакет в 0.5.0, ядро стало
самодостаточным. Обнаружение и транспорт измерены на живом железе (см. «Что показал провод»), а
`YandexMusic.LocalDevices` уже существует в ветке `local-devices`: обнаружение реализовано и
проверено. Неизвестными остаются аутентификация и схема команд, поэтому **управлять** пока нечем.

## Проблема

Пульт Ynison показывает только те устройства, которые вошли в Ynison-сессию аккаунта. В снятом с
живой сессии кадре (журнал запросов, клавиша `g` в меню) их ровно четыре:

| device_id | название | тип | офлайн | can_be_player |
|---|---|---|---|---|
| `71627e95…` | OnePlus CPH2747 | ANDROID | нет | да |
| `<это приложение>` | YandexMusic .NET | WEB | нет | нет |
| `5315b78…` | YandexMusic .NET | WEB | да | нет |
| `dbf5653…` | YandexMusic .NET | WEB | да | нет |

Колонок нет вообще — ни в простое, ни в каком-либо виде, и в кадре нет поля, которое могло бы их
скрывать. Сервер просто не помещает их в сессию.

При этом официальное приложение предлагает колонки в той же сети Wi-Fi **даже когда на колонке чужой
аккаунт**. Протокол уровня аккаунта так не умеет по построению. Значит, список устройств в
официальном клиенте — объединение двух источников:

1. **Ynison** — устройства *этого аккаунта*, находящиеся в сессии. Уже реализовано.
2. **Локальное обнаружение** — всё, что откликнулось *в этой сети*, независимо от аккаунта. Нет.

Этот issue — про второй источник и про перестройку репозитория, которой он требует.

## Почему это требует перестройки

Сейчас `YandexMusic` — один пакет, содержащий и REST API, и Ynison, связанные через
`IYandexMusicClient.CreateYnisonClient()`. Добавить в тот же пакет третью подсистему — значит
заставить каждого потребителя REST API таскать за собой websocket-клиент, mDNS-ответчик и локальный
TLS-стек, которые он никогда не вызовет.

Подавляющему большинству нужен REST API и ничего больше. Это должно остаться правдой.

### Целевая раскладка

```
YandexMusic                 REST Music API. Зависит только от BCL.
YandexMusic.Ynison          Состояние и пульт уровня аккаунта. Зависит от YandexMusic.
YandexMusic.LocalDevices    Обнаружение и управление в своей сети. Зависит от YandexMusic.
YandexMusic.DependencyInjection   Без изменений: AddYandexMusic() для ядра.
```

Правила:

- `YandexMusic` никогда не ссылается на два других. Он самодостаточен и полезен сам по себе — это то
  ограничение, под которое подстраивается всё остальное.
- `YandexMusic.Ynison` и `YandexMusic.LocalDevices` не ссылаются друг на друга. Кому нужен объединённый
  список устройств, как в официальном приложении, берёт оба и объединяет сам; помощник, который делает
  объединение, может появиться позже отдельным пакетом, когда обе половины будут готовы.
- Все три выпускаются из этого репозитория на одной версионной линии, чтобы «репозиторий YandexMusic
  закрывает все потребности по работе с сервисом» выполнялось без разнесения работы по репозиториям.

### Единственное ломающее изменение, которое для этого нужно — сделано в 0.5.0

`IYandexMusicClient.CreateYnisonClient()` — та самая связка, которая мешала разделению: интерфейс ядра
называл тип из Ynison. Метод уехал из ядра и стал методом расширения, которое поставляет пакет Ynison:

```csharp
// до 0.5.0, на интерфейсе ядра
IYnisonClient CreateYnisonClient(string? deviceId = null, YnisonClientOptions? options = null);

// с 0.5.0, в YandexMusic.Ynison
public static class YandexMusicClientYnisonExtensions
{
    public static IYnisonClient CreateYnisonClient(
        this IYandexMusicClient client,
        string? deviceId = null,
        YnisonClientOptions? options = null);
}
```

Места вызова не изменились — `client.CreateYnisonClient()` по-прежнему компилируется, — но теперь
нужен `using YandexMusic.Ynison;`, а из интерфейса ядра метод исчез. Токен берётся из
`client.Authentication.Session.AccessToken`, он и так был публичным.

Заодно уехали две мелочи, невидимые для вызывающего кода: `YandexMusicYnisonException` теперь
поставляется из сборки Ynison (namespace не менялся, так что блоки `catch` компилируются как прежде),
и вместе с ним переехали protobuf-JSON-конвертеры — других потребителей у них не было. Ядро больше
вообще не ссылается на `System.Net.WebSockets`.

`YandexMusic.LocalDevices` получает такое же оформление, чтобы все три точки входа читались одинаково.

## Объём YandexMusic.LocalDevices

Три отделимых части, в порядке зависимости:

1. **Обнаружение.** Найти колонки в текущей сети и сообщить id, имя, модель, адрес и доступность.
   Чисто локально, аккаунт не участвует.
2. **Авторизация.** Получить то, что требует локальный канал управления. Именно эта часть трогает
   бэкенд Яндекса и именно она понята хуже всего.
3. **Управление.** Подключиться к устройству и рулить им: play/pause, следующий/предыдущий, громкость,
   статус.

Разумная первая веха — **только обнаружение**: `LocalDeviceScanner`, возвращающий то, что есть в сети.
Оно ценно само по себе (пульт сможет показать колонки серым и объяснить, почему ими пока нельзя
управлять), проверяется без каких-либо учётных данных и снимает риск с остального.

### Поверхность, как она получилась

```csharp
public interface ILocalDeviceScanner
{
    IAsyncEnumerable<LocalDevice> DiscoverAsync(TimeSpan window, CancellationToken cancellationToken = default);
}
```

`IAsyncEnumerable`, а не список: обнаружение — это поток ответов, приходящих в течение окна, и UI
хочет показывать каждое устройство в момент его отклика.

`LocalDevice` отличается от наброска в одном месте, которое стоит отметить: поля `Name` больше нет.
Устройства не сообщают имя, которое им дал владелец, так что в это поле можно было бы положить только
выдумку. Вместо него есть `DeviceId`, `Platform`, `Endpoint`, `Host` и сырые `Attributes` — всё
измеренное, а не предположенное.

## Что показал провод

Снято на четырёх колонках (Мини, Станция 2, Станция 3, Станция Миди) в одной домашней Wi-Fi-сети
22.08.2026. Всё в этом разделе наблюдалось напрямую, а не выведено по аналогии: ответы обнаружения,
TLS-рукопожатие и апгрейд до websocket. Ни одной команды устройствам не отправлялось.

### Обнаружение — mDNS/DNS-SD, `_yandexio._tcp`

Гипотеза подтвердилась. `_services._dns-sd._udp.local` перечисляет `_yandexio._tcp.local`, а
PTR-запрос по нему возвращает по одному экземпляру на колонку. Каждый экземпляр раскрывается в:

| Запись | Содержимое |
|---|---|
| PTR | `YandexIOReceiver-<deviceId>._yandexio._tcp.local` |
| SRV | `<модель>-<deviceId>.local` : **1961**, priority 0, weight 0 |
| TXT | `deviceId=<id>`, `platform=<модель>`, `cluster=yes` |
| A / AAAA | адрес в сети плюс link-local IPv6 |

`platform` — это ключ модели: `yandexmini`, `yandexstation_2`, `orion` (Станция 3), `cucumber`
(Станция Миди). Именно его интерфейс должен превращать в читаемое название; в имени mDNS-экземпляра
никакой пользовательской подписи нет, поэтому понятное имя, которое человек узнаёт («Колонка на
кухне»), локально **недоступно** и должно приходить из аккаунтного источника.

Две практические заметки для реализации. Порт лежит в SRV-записи, и читать его надо оттуда, а не
зашивать в код, — 1961 сообщают эти четыре. И одна колонка объявила обобщённое имя хоста
(`Android.local`) вместо производного от модели, так что имя хоста — ненадёжная идентичность:
идентичность — это `deviceId` из TXT.

### Транспорт — TLS 1.2 с самоподписанным сертификатом, дальше WebSocket

Порт 1961 отвечает рукопожатием TLS 1.2, шифр `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`, сертификат:

```
subject: O=Yandex, CN=localhost, C=RU
issuer:  O=Yandex, CN=localhost, C=RU     (самоподписанный)
```

Проверка проваливается по двум причинам, по построению и навсегда: `RemoteCertificateChainErrors`
(самоподписанный, пути до публичного корня нет) и `RemoteCertificateNameMismatch` (`CN=localhost`
никогда не совпадёт с адресом, к которому подключаются). **И истечение срока — не гипотеза**: из
четырёх колонок одна отдаёт сертификат, истёкший в 2024 году, и продолжает работать. Политика
проверки, отвергающая просроченные сертификаты, делает эту колонку неуправляемой навсегда.

Поэтому проверка сертификата обязана быть осознанным и задокументированным решением. Она не может
быть поведением по умолчанию, но и «молча принимаем всё» тоже не годится. Это самый требовательный к
аккуратности вопрос во всём пакете.

Поверх TLS устройство говорит по **WebSocket** — `Server: WebSocket++/0.8.2`. Апгрейд принимается
**вообще без каких-либо учётных данных**: ни токена, ни заголовка, ни предварительного сопряжения.
Сразу после 101 устройство начинает слать websocket-фреймы Ping с полезной нагрузкой `server_ping`.

Значит, аутентификация — на уровне сообщений, а не соединения. И значит, обнаружение и подключение
можно реализовать и проверить вообще без участия аккаунта.

### Учётные данные — токен на устройство от бэкенда quasar

Два недокументированных эндпоинта, оба отвечают `200` и `status: ok` при вызове с OAuth-токеном
аккаунта в заголовке `Authorization: OAuth <токен>`:

```
GET https://quasar.yandex.net/glagol/device_list
GET https://quasar.yandex.net/glagol/token?device_id=<id>&platform=<platform>
```

`device_list` возвращает все устройства Quasar на аккаунте — **не только колонки**: на доме с четырьмя
колонками там же оказались камера (`platform: mike`) и семь регистраций телефонных приложений
(`alice_app_android`, `iot_app_android`). `networkInfo` есть не у всех, а только у тех, кто недавно
был доступен в локальной сети. Всему, что управляет воспроизведением, придётся фильтровать.

У каждой записи, помимо объёмного блока `config`:

| Поле | Содержимое |
|---|---|
| `id` | тот же идентификатор, что mDNS отдаёт как `deviceId` — совпадают точно |
| `name` | **имя, которое колонке дал владелец**; в mDNS его нет |
| `platform` | тот же ключ модели, что и в mDNS |
| `glagol.security.server_certificate` | TLS-сертификат устройства, ~1050 символов |
| `glagol.security.server_private_key` | приватный TLS-ключ устройства, ~1675 символов |
| `networkInfo` | `external_port` (1961), `ip_addresses`, `mac_addresses`, `wifi_ssid`, `ts` |

`glagol/token` дальше возвращает токен на устройство, примерно 200–230 символов. У каждого свой.

Две заметки для того, кто будет писать модели. JSON смешивает соглашения — `networkInfo` в camelCase,
а `external_port` и `ip_addresses` внутри него в snake_case, — так что одной политикой именования не
обойтись, snake_case-полям нужны явные имена. И `device_list` несёт массу всего, не имеющего отношения
к музыке: координаты дома, имя Wi-Fi-сети, MAC-адреса и коды активации. Модели должны разбирать то,
что нужно функции, а остальное не читать.

### Это закрывает вопрос с TLS: пиннинг, а не доверие

`server_certificate` — это собственный сертификат устройства, который отдаёт бэкенд. Значит клиенту не
нужно выбирать между «принимаем всё» и «отвергаем всё»: он может сверить предъявленный колонкой
сертификат с тем, который бэкенд назвал сертификатом этой колонки, и отказать всему остальному. Это
настоящий пиннинг, и именно так пакет и будет устроен.

Заодно снимается проблема просроченного сертификата. Пиннинг сравнивает сам сертификат, поэтому
колонка, до сих пор отдающая сертификат с истёкшим в 2024 году сроком, остаётся полностью рабочей, а
подменённый сертификат всё равно отвергается. Проверка дат дала бы здесь ровно обратное безопасности:
заблокировала бы настоящее устройство, ничего не доказав про любое другое.

`server_private_key` — другое дело. Это приватный ключ устройства, и зачем бэкенд вообще отдаёт его
клиентам, непонятно. Пиннингу он не нужен, поэтому пакет **не будет его ни запрашивать, ни хранить**.
Это осознанное решение, записанное здесь, чтобы его потом молча не отменил тот, кто решит, что
неиспользуемое поле безобидно сохранить.

Пиннинг не просто правдоподобен, он измерен: сертификат, который `device_list` называет сертификатом
конкретной колонки, и сертификат, который эта колонка предъявляет на порту 1961, имеют одинаковый
отпечаток — проверено на двух устройствах в разных прогонах. Сравнение — `GetCertHashString()` у
разобранного PEM из `device_list` против сертификата, переданного в колбэк проверки.

### Системный прокси надо отключать явно

`ClientWebSocket` по умолчанию уважает настроенный на машине прокси, и делает это в том числе для
адресов локальной сети. На машине с системным прокси подключение к `wss://192.168.x.x:1961`
превращается в запрос `CONNECT` к прокси, тот отвечает `403`, и всё это всплывает как совершенно
бесполезное «Unable to connect to the remote server» — причём колбэк проверки сертификата не
вызывается вообще, потому что до рукопожатия дело не доходит.

Поэтому клиент управления обязан ставить `Options.Proxy = null`. Ничто в локальной сети не должно
ходить через прокси, а отдав это на откуп настройкам машины, получим функцию, которая работает на
ноутбуке разработчика и не работает ни на одном корпоративном.

### Колонки молчат, пока к ним не обратятся

Клиент, который подключился и молчит, не получает никаких прикладных данных вообще — двадцать секунд
открытого сокета дали ноль кадров. Устройство шлёт служебные websocket-ping, но их обрабатывает
уровень протокола, и до приложения они не доходят.

Значит выучить схему сообщений одним наблюдением нельзя. И значит первое, что должен отправить клиент
управления, — это запрос статуса.

### Цена зависимости — ответ: зависимость не нужна

Весь путь обнаружения выше отработал на самописном DNS-SD запросе и разборе примерно в 150 строк.
Один PTR-запрос плюс разбор записей PTR/SRV/TXT/A — вместе со сжатием имён — это весь mDNS, который
нужен пакету. Тащить ради этого Makaretu.Dns или Zeroconf в библиотеку, чьё главное свойство — ядро
без зависимостей, не стоит.

### Схема сообщений

Снята отправкой единственного `ping` — запроса статуса, который ничего не меняет, — и чтением ответа.
Запрос это один текстовый websocket-кадр:

```json
{
  "conversationToken": "<токен на устройство из glagol/token>",
  "id": "<uuid, который придумывает вызывающий>",
  "sentTime": 1787425216425,
  "payload": { "command": "ping" }
}
```

Ответ возвращает `id` как `requestId` и `sentTime` как `requestSentTime` — то есть ответы можно
сопоставлять с запросами, — и несёт `status` (`SUCCESS`), `sentTime`, `processingTime`, два больших
блока, бесполезных музыкальному клиенту (`experiments` и `extra` с base64-протобуфом `appState`),
списки возможностей устройства и то, ради чего всё затевалось:

```
state
  aliceState                IDLE
  playing                   true
  volume                    0.3            0..1
  canStop                   true
  timeSinceLastVoiceActivity 373
  hdmi { capable, present }
  playerState
    id, title, subtitle     трек, его название и исполнитель
    type                    Track
    duration                168            СЕКУНДЫ, не миллисекунды
    progress                67.11          секунды, дробные
    hasPlay, hasPause       что возможно ПРЯМО СЕЙЧАС, а не что устройство умеет:
    hasNext, hasPrev        во время игры hasPause=true, а hasPlay=false
    hasProgressBar
    playerType              music_thin
    playlistId, playlistType, playlistPuid, playlistDescription
    entityInfo { id, type, repeatMode, next { id, type }, prev { id, type } }
    extra { coverURI, radioSessionID, requestID, stateType }
    liveStreamText, showPlayer
```

Обратите внимание на единицы: `duration` и `progress` здесь в **секундах**, тогда как в Ynison —
миллисекунды. Клиенту, который сводит прогресс из обоих источников в одну полосу, придётся приводить.

`supported_features` перечисляет 29 возможностей — `absolute_volume_change`, `relative_volume_change`,
`multiroom`, `stereo_pair`, `bluetooth_player`, `audio_bitrate320` и прочее. Это описание того, что
умеет железо, а не словарь команд.

### Это поток состояния, а не запрос-ответ

Один `ping` дал **четырнадцать** ответов за следующие двенадцать секунд. То есть устройство не
отвечает на вопрос и замолкает: после первого валидного сообщения оно начинает присылать состояние на
каждое изменение. Поэтому форма этого клиента гораздо ближе к `IYnisonClient`, чем к группам REST-
эндпоинтов: подключиться, отправить одно сообщение, чтобы начать разговор, дальше подписаться.

### Словарь команд

Каждая отправлена на живую колонку, и эффект подтверждён свежим `ping` через три секунды, а не взят
из ответа на саму команду:

| `payload.command` | Действие | Статус |
|---|---|---|
| `ping` | возвращает состояние, ничего не меняет | `SUCCESS` |
| `play` | продолжает воспроизведение | `SUCCESS` |
| `stop` | **ставит на паузу** — это и есть команда паузы | `SUCCESS` |
| `next` | следующий трек | `SUCCESS` |
| `prev` | предыдущий трек | `SUCCESS` |
| `setVolume` + `volume` (0..1) | ставит громкость | `SUCCESS` |
| `rewind` + `position`? | принимается, но перемотки не наблюдалось | `SUCCESS` |
| `pause` | **такой команды нет** | `UNSUPPORTED` |
| что угодно неизвестное | | `UNSUPPORTED` |

`pause` заслуживает отдельной строки, потому что это очевидная догадка и она неверна: устройство
отвечает `UNSUPPORTED`, а пауза — это `stop`. Неизвестная команда отвергается тем же статусом, а не
проглатывается молча, — значит у библиотеки есть настоящий сигнал об ошибке.

`rewind` принимается, а не отвергается, то есть команда существует, — но `position: 5` не дал
наблюдаемой перемотки, так что имя аргумента остаётся догадкой.

### Две ловушки в ответе, обе стоит знать до написания клиента

**Ответ несёт состояние ДО применения команды.** `stop` возвращает кадр с `playing: true`, а через
три секунды устройство сообщает `playing: false`. Команда сработала, просто в ответе снимок на момент
приёма сообщения. Тот, кто станет проверять результат по ответу самой команды, будет каждый раз
получать вывод, что ничего не произошло.

**Не на каждую команду вообще приходит ответ.** На `play` в двух прогонах не пришло ни одного кадра с
его `requestId`, хотя команда очевидно отработала. То есть `requestId` полезен, чтобы сопоставить
ответ, когда он есть, но ждать его как подтверждения нельзя. Единственный надёжный источник правды о
том, что делает устройство, — поток состояния.

## Открытые вопросы — всё ещё без ответа

- **Аргумент `rewind`.** Команда существует; как сказать ей, куда перематывать, из измеренного не
  следует.
- **Управление под чужим аккаунтом.** Официальное приложение управляет колонками с чужими аккаунтами.
  Верно ли это для любого устройства в сети или только в каком-то состоянии сопряжения — это
  существенно меняет модель безопасности функции и должно быть понято до выпуска. Заметьте: всё
  измеренное здесь шло через `device_list`, привязанный к аккаунту, — так что этот путь **не**
  объясняет, как официальное приложение достаёт до чужой колонки.
- **Охват платформ.** Обнаружение подтверждено на Windows. Поведение mDNS различается на Linux/macOS
  и ломается во многих корпоративных и гостевых сетях; библиотека должна аккуратно вырождаться в
  «ничего не найдено», а не зависать. Отдельно: на машине с несколькими адаптерами (Hyper-V, WSL, VPN)
  сокет, привязанный к `0.0.0.0`, отправит запрос через тот адаптер, который выиграет по метрике
  маршрута, — здесь это не нашло вообще ничего. Обнаружение обязано опрашивать **каждый** интерфейс
  явно.

## Вне объёма

- Обёртка над платформой умного дома вообще (лампы, розетки, сценарии). Речь только о точках
  воспроизведения музыки.
- Объединение двух списков устройств внутри любого из пакетов. Это уровнем выше обоих.
- Голосовое взаимодействие с ассистентом.
